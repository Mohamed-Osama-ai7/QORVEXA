# QORVEXA Benchmark Authoring Guidelines (v1)

> **Core Invariant:** Ground truth and benchmark metadata must be honest, reproducible, and verifiable. Never fabricate OEM manuals, fake Arabic field data, or label development cases as held-out test data.

---

## 1. Split Taxonomy & Lifecycle

Benchmark cases belong to one of five mutually exclusive splits:

| Split | Purpose | Evaluated In | Included in Quality Averages? | Leakage Rule |
|---|---|---|---|---|
| `development` | Exploration, parameter tuning, baseline checks | Ordinary runs (`rca`, `retrieval`, `rca-run`) | Yes | May not be promoted to `validation` or `test` |
| `validation` | Hyperparameter selection, checkpoint ranking | Ordinary runs (when specified) | Yes | Must not overlap with `development` authoring |
| `test` | Frozen final evaluation | `--final` runs only | Yes (gated) | Requires `authored_independent`, adjudicator review, clean Git state |
| `fixture` | Contract verification of scoring code & metrics | Ordinary runs | **No** (excluded from quality averages) | Scored to verify metrics; never mixed with domain performance |
| `unassigned` | Legacy or unvetted cases | Ordinary runs | Yes (with warning) | Default for unvetted cases |

### Ordinary vs Final Runs
* **Ordinary runs (`python -m factorymind.evaluation rca / retrieval / rca-run`)**:
  Refuse any case with `split="test"` (raises `SplitError`). Test cases cannot be run casually or repeatedly during development.
* **Final runs (`--final`)**:
  Evaluate **only** cases with `split="test"`. Requires clean Git state, valid frozen splits manifest (`splits.v1.json`), verified dataset and corpus hashes, and candidate code fingerprint. Appends run details to `artifacts/evaluations/ledger.jsonl`.

## 2. Origin Taxonomy

The `origin` block records provenance and authorship without inventing evidence:

| Origin Kind | Definition | Required Fields | Permitted Splits |
|---|---|---|---|
| `authored_team` | Authored by core project development team | `kind` | `development`, `unassigned` |
| `authored_independent` | Authored by independent engineers/annotators outside core development | `kind`, `author_id` | `test`, `validation`, `development` |
| `derived_from_dev` | Derived from or modified after observing development failures | `kind`, `derived_from` | `development`, `unassigned` |
| `observed_dataset` | Direct telemetry or operator failure report from operational dataset | `kind`, `derived_from` | `development` (F1–F4 are `development`) |
| `synthetic_generated` | Synthetically generated from physical models or scenario generators | `kind` | `development`, `unassigned` |
| `contract_fixture` | Adversarial test case designed to test scoring and edge-cases | `kind` | `fixture` |
| `unknown` | Origin unknown or unrecorded | `kind` | `unassigned` |

## 3. Dependence & Clustering (`cluster_id`)

Statistical intervals rely on truthful dependence modeling:
* **Definition:** A cluster is a unit of sampling dependence. Cases sharing an underlying source event, document section, failure incident, or paraphrase root must share a `cluster_id`.
* **RCA:** For MetroPT-3 observed failure reports, each operator report (e.g., F1, F2, F3, F4) defines its own cluster (`metropt3-f1`, `metropt3-f2`, etc.).
* **Retrieval:** Paraphrases or related queries targeting the same source document chunk or maintenance procedure must share a `cluster_id`.
* **Rules:**
  - Cluster bootstrap requires $N \ge 30$ observations and $K \ge 10$ independent clusters.
  - If cases lack a `cluster_id` or dependence is unknown, intervals are marked `unavailable`. Never silently fall back to an item-level bootstrap when cluster dependence exists.

## 4. Retrieval Relevance & Content Rules

Retrieval cases in `rca_case/v1` and `retrieval_case/v1` require explicit provenance:

### Content Origin
- `native`: Query written natively in the target language (e.g. English technical manual query).
- `translated`: Query translated from another language. Requires `translation_of` (original case ID) and `translator` (author or tool).
- `synthetic`: Query generated by prompt or model.

### Relevance Source
- `author_asserted`: Relevant chunks asserted by query author.
- `annotator_labelled`: Labeled by external annotator (`annotator_ids` required).
- `pooled_adjudicated`: Pooled from multiple retrievers and adjudicated by experts (`annotator_ids` required).
- `inherited_prefix_v0`: Legacy prefix matching from v0 cases.

### Chunk Provenance & Stale Label Protection
- `source_chunk_ids`: Exact chunk IDs known to contain the relevant information.
- `source_chunk_sha256`: Map from chunk ID to SHA-256 of its text when labeled. If the corpus text changes, evaluation detects `stale_label` and refuses stale scoring.

## 5. Bilingual & Arabic Language Policy

1. **Current Status:**
   - Arabic industrial retrieval claims **remain disabled**.
   - Current lexical tokenizers use ASCII patterns (`[a-z0-9_]+`) and produce 0 tokens for Arabic text.
   - Arabic evaluation is blocked until decisions **D-1** (OEM Arabic documentation) and **D-2** (native Arabic technical corpus) are resolved.
2. **Tokenizer Diagnostics:**
   - Run `diagnose_arabic_tokenization(text)` to verify orthography.
   - Diagnoses tashkeel (diacritics), tatweel (kashida), hamza variants (أ, إ, آ, ٱ), taa marbuta (ة), and alif maqsura (ى).
   - If a tokenizer produces 0 tokens for an Arabic query, evaluation returns `unsupported_language` rather than reporting 0 recall or false out-of-scope abstention.

## 6. Leakage Auditing Before Case Acceptance

Before committing or freezing benchmark cases, run the leakage audit:
```bash
uv run python -m factorymind.evaluation audit --retrieval benchmarks/qorvexa/retrieval_cases.v1.jsonl --rca benchmarks/qorvexa/rca_cases.v1.jsonl
```

The audit checks:
1. **Query Near-Duplicates:** Normalized token Jaccard similarity $\ge 0.80$.
2. **Query-to-Document Copying:** Verbatim copying or token containment $\ge 0.70$.
3. **Author Overlap:** Test case authors overlapping with dev authors.
4. **Event Window Overlap:** Temporal intersections between RCA cases.
5. **Detector Training Window Overlap:** Overlap with MetroPT-3 training/calibration windows (`2020-02-01` to `2020-04-01`).
